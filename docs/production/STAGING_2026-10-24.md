## Reprendre sans recréer ni exposer les ressources

Définir `CLOUDFLARE_ACCOUNT_ID` et `AIRA_STAGING_D1_ID` avec les identifiants
non secrets ci-dessus. Après build et tests :

```sh
node scripts/cloudflare-config.mjs staging --database-only
npx --no-install wrangler d1 migrations list DB --remote --config .wrangler/deploy/staging-db-only.json
npx --no-install wrangler secret list --config .wrangler/deploy/staging-db-only.json
npx --no-install wrangler deploy --config .wrangler/deploy/staging-db-only.json
npx --no-install wrangler deployments list --name aira-staging --json
```

Pour répéter le contrôle du bundle distant, sans tunnel public :

```sh
npx --no-install wrangler dev --remote --config .wrangler/deploy/staging-db-only.json --ip 127.0.0.1 --port 4199 --inspector-port 0
curl -i http://127.0.0.1:4199/api/health
curl -i http://127.0.0.1:4199/api/workspace
curl -i http://127.0.0.1:4199/auth/sign-in
```

Ces lectures ont accès aux bindings distants : utiliser uniquement ce manifeste
de staging et arrêter le proxy après le test. Ne pas ajouter de fausse identité.

Après R2 : inventaire, création des deux buckets **s'ils sont absents**, variables
`AIRA_STAGING_FILES_BUCKET`/`AIRA_STAGING_BACKUPS_BUCKET`, génération du manifeste
complet, puis déploiement privé. Ne pas activer les flags de recette sans preuve.

Ajouter les clés manquantes dans les secrets du Worker, depuis le tableau de bord
ou `wrangler secret put NOM --config .wrangler/deploy/staging-db-only.json` avec
saisie privée. Ne jamais les placer dans un argument, fichier versionné ou message.
Le contrôle du panneau droit n'est pas disponible dans la session actuelle.
